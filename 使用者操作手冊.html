1. 這套系統是什麼

EQ Performance Dashboard 是一個入口／看板聚合平台。它自己不產生報表，而是把散落在廠內各處的效能報表、看板、工具網頁， 依照每個人的廠區與職務權限整理成一份「他該看到的目錄」，再用統一的介面（內嵌、分頁、全螢幕）打開。

它解決什麼問題
  • 報表網址四散、沒人記得住
  • 不同廠區、不同部門該看的東西不同
  • 誰看過什麼、誰在用哪張看板，沒有紀錄
它提供什麼
  • 依權限自動生成的多層選單
  • 個人化版面（自訂順序與捷徑）
  • 三語介面（繁中／English／日本語）
  • 操作稽核與使用率統計

3. 登入是怎麼運作的 所有人

系統有三條可能的身分來源，實際用哪一條由設定決定：

① Windows 自動偵測（Negotiate） ← 正式站唯一使用的方式 ② 模擬他人帳號（SimulatedAccount）← 測試站專用，全站生效 ③ 手動帳密 + LDAP / 測試帳號 ← 程式支援，但正式環境政策禁用

3.1 正常情況下你會看到什麼

  1. 打開網址 → 出現「正在偵測桌機登入者…」
  2. 偵測成功 → 直接進入主畫面，完全不需要輸入帳密
  3. 偵測失敗 → 停在登入框，可按「重試偵測」
⚠ 瀏覽器跳出「輸入網路密碼」對話框怎麼辦

這不是系統壞掉，是瀏覽器不信任這個站台，所以不肯自動送出 Windows 身分。Negotiate 的 401 挑戰是協定必要步驟，伺服器端無法迴避。

  • 正解（全廠做法）：請 IT 用 GPO 推 Edge/Chrome 原則 AuthServerAllowlist，把站台主機名加進去。這比叫每個人改「網際網路選項」實際得多。
  • 單機臨時解：Edge → 設定 → 隱私權與安全性 → 安全性 → 近端內部網路 → 加入 http://主機名，並勾「自動以目前的使用者名稱及密碼登入」。
  • 先檢查這三件事：① 用的是單一標籤主機名（如 http://p58esiap12，不含點）還是 FQDN／IP？前者本來就會被自動歸類為近端內部網路，仍跳視窗代表 ② 「自動偵測內部網路」被 GPO 關掉，或 ③ 該區域的「登入」被設成提示。

3.2 登入多久會過期

  • Auth:SessionDays 預設 3650 天 + 滑動式展延 → 實務上不會過期，隔夜或放長假回來都不用重登入。
  • 遇到 401 時前端會先靜默重新自動登入，成功的話只出現一個右下角提示、留在原頁，不會彈視窗。
  • 唯一會讓所有人一起被登出的動作：刪掉 App_Data/keys（DataProtection 金鑰，Cookie 是用它加密的）。部署或搬機器務必保留該目錄。

3.3 我登入了卻看到「無權限」

代表身分驗證成功、但授權失敗。依序檢查：

  1. 這個工號在「帳號管理」裡建立了嗎？
  2. 它有沒有勾選任何可視群組版面（Role）？沒有 Role＝看不到任何看板。
  3. 它的 Role 有沒有被綁到目前這個廠區？（廠區管理 → 套用的權限群組）
  4. Auth:OpenAccessMode 是否為 false？若為 true，未建檔的人會自動建帳並綁全廠區；若為 false，嚴格限制名單。

4. 切換自動偵測 ⇄ 模擬他人帳號 部署／IT

模擬帳號是刻意提供的測試工具：指定一個工號後，這個站台的所有訪客都會被當成那個人，用來驗證「某人看到的畫面與權限到底長什麼樣」。

⛔ 使用前提 因為是全域生效（所有訪客共用同一個身分），而且每次變更都會作廢所有人的 Cookie， 所以只能掛在測試站（例如 EQDashboard_TEST）。正式站必須留空。

4.1 先理解設定優先序

appsettings.json → appsettings.{環境}.json → 環境變數（最高，蓋過前兩者） （開發預設值） （Production 覆寫） （web.config / App Pool）

appsettings.Production.json 已經把 Auth:SimulatedAccount 釘成空字串， 所以 Production 的預設恆為「不模擬」，切換完全由 web.config 的「設定區 B-2」決定。

4.2 切成模擬他人帳號

  1. 打開站台目錄下的 web.config，找到 「設定區 B-2：模擬他人帳號」。
  2. 把註解拿掉，填入要模擬的工號。兩條都要有： 
    <environmentVariable name="Auth__SimulatedAccount"                  value="00058896" />
<environmentVariable name="Auth__AllowSimulatedAccountInProduction" value="true" />
  3. 存檔即可，不需要 iisreset。 ANCM 會監看 web.config，存檔就自動回收 App Pool。
  4. 驗收：打開 logs\log-*.txt，看到這行代表生效 —— 
    ⚠️ 模擬帳號已啟用：Auth:SimulatedAccount = "00058896"
  5. 使用者端不用做任何事：模擬帳號一變更，所有 Cookie 立刻作廢，前端會靜默重新登入，只會看到一個提示。

4.3 切回 Windows 自動偵測

  1. 把 §4.2 那兩條環境變數整段註解掉（或刪除）。
  2. 存檔，一樣自動回收。
  3. 驗收：logs\log-*.txt 不再出現「模擬帳號已啟用」那一行＝已回到自動偵測。
⛔ 這裡踩過一個坑，值得記住

在 appsettings.Production.json 補上 "SimulatedAccount": "" 之前，把 B-2 註解掉會讓設定 往下退回 appsettings.json 的 "00058897"，同時放行旗標也退回預設 false → 啟動守衛再次拒絕啟動，畫面是一片空白的 HTTP 500.30。

通則：任何「靠註解掉環境變數來關掉某功能」的操作，都要先確認 appsettings*.json 的底值是安全的， 否則關掉的瞬間會退回一個你沒預期的值。

現場臨時切回、又不確定環境時：寧可把 Auth__SimulatedAccount 的 value 清成 "" 並 保留旗標 true，也不要整段註解掉 —— 萬一空字串沒吃到，站台至少還會啟動、log 一眼看得出來， 而不是給你一片查不出原因的 500.30。

⚠ 三個常見誤判
  • 看到的工號不是你剛填的 → 進程沒有真的重啟，不是設定寫錯。
  • 模擬後看到「無權限」畫面 → 那是權限判定正常運作。被模擬的工號不在 Accounts 表、也不在 DefaultAdmins、且 OpenAccessMode=false 就會這樣。請先去「帳號管理」把人建起來。
  • 改完仍 500.30 → 先看守衛列出哪幾項。Password=test 那項是獨立的（連線字串問題），跟模擬帳號無關，別誤判成「模擬帳號沒關掉」。看不到原因時暫時把 web.config 的 stdoutLogEnabled 改 true。
ℹ 不要用別的方式切換 不要為了切回自動偵測去改 appsettings.json（那是 Development 用的值，而且下次 dotnet publish 會蓋回去）， 也不要為了讓模擬帳號通過守衛而把整站降成 Development（那會一併放行測試帳號等所有高風險設定）。

5. 本機開發：切換成 LDAP／手動帳密登入 部署／IT

⛔ 先講結論：這條路只能在本機用

「手動登入 + LDAP」在程式面完整可用（AuthService.VerifyLdapPasswordAsync、AuthController.Login）， 但企業內網 IIS 政策不允許啟用（2026-08-25 定案）。所以：

  • 可以：在本機 localhost 開發／驗證 LDAP 邏輯。
  • 不可以：把它當成正式站的登入方案，或作為「投影機上換帳號」的解法。

5.1 本機環境長什麼樣

  • 啟動設定在 Properties/launchSettings.json：ASPNETCORE_ENVIRONMENT=Development，網址 http://localhost:5242（https 為 https://localhost:7033）。
  • Development 環境不會觸發啟動守衛拒絕啟動，只會印警告 → 本機可以自由開測試帳號與 LDAP。

5.2 開啟 LDAP 登入的步驟

  1. 編輯 appsettings.Development.json（這個檔目前只有 Logging 設定，把 Auth 段整段加進去）： 
    {
  "Logging": {
    "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" }
  },
  "Auth": {
    "AllowManualLogin": true,
    "TestAccounts": { "Enabled": false },
    "Ldap": {
      "Enabled": true,
      "Server": "實際的 AD 伺服器位址",
      "Port": 389,
      "UseSsl": false,
      "BindDomain": "UMC",
      "SearchBase": "DC=umc,DC=com",
      "UserPrincipalSuffix": "@umc.com"
    }
  }
}
  2. 重新啟動（dotnet run 或 Visual Studio F5）。設定檔是啟動時讀取的。
  3. 驗收：瀏覽器打開 http://localhost:5242/api/Auth/Config，回傳的 JSON 內 allowManualLogin 應為 true。
  4. 測試登入：POST /api/Auth/Login，body 為 {"empId":"工號","password":"密碼"}。
⚠ 目前介面上沒有帳密輸入框

wwwroot/index.html 的登入框只保留了「Windows 自動偵測」那一塊（#pane-windows）。 auth.js 的 doLogin() 仍在，但它要找的 #empId、#empPwd、#manual-login-error 三個元素已不存在於 HTML。

所以把 AllowManualLogin 打開後，畫面上不會自動長出登入表單。要在本機用介面測 LDAP，兩條路：

  1. 推薦：直接打 API（如上一步），用 Postman / curl / 瀏覽器 devtools 驗證 LDAP bind 是否成功。
  2. 或自行在 index.html 的 #login-overlay 內補回一段表單，欄位 id 必須是 empId / empPwd / manual-login-error，送出時呼叫 doLogin()。

5.3 驗證優先序（後端 Login 端點的實際順序）

  1. AllowManualLogin=false → 直接擋掉，回 err_manual_login_disabled。
  2. TestAccounts 白名單：工號＋密碼比對成功 → 來源標記 test。
  3. EnableEmergencyAdmin：工號為 admin 且旗標開啟 → 不檢查密碼直接放行（純救援通道，極危險）。
  4. LDAP bind：以上都不符 → 連 AD 驗證。密碼錯誤（LDAP error 49）回 err_auth_failed。

另外：POST /api/Auth/Login 有速率限制，每個 IP 每 60 秒最多 10 次，用來擋暴力破解。

選項行為什麼時候用

  • 為什麼要有這張卡：以前這種看板只會開新分頁、本站畫面原封不動留著上一個看板。 從新分頁切回來時很容易誤以為「現在看到的就是我剛點的看板」—— 尤其是點上方導覽列時（系統會自動開啟該分類左側選單的第一個看板，那個殘留畫面根本不是你選的）。
  • 新分頁沒跳出來：多半是瀏覽器的快顯（彈出視窗）封鎖擋掉了。 按提示卡上的重新開啟即可；不小心把新分頁關掉時也用同一顆按鈕。
⚠ 嵌入後畫面一片空白 / 顯示「未識別」/ 表格抓不到資料

這是最常被誤判成「後端壞掉」的問題。判斷方法：把同一個網址單獨開一個分頁。

  • 另開分頁正常、嵌在裡面壞掉 → 幾乎都是 iframe 隔離造成的，不是後端也不是 DB。
  • 目標網站設了 X-Frame-Options / CSP frame-ancestors → 它本來就拒絕被嵌入。解法：把開啟方式改成「新分頁」或「新視窗開啟」。
  • 儀表板與看板不在同一台主機 → 看板的 session cookie 在 iframe 內屬第三方 cookie，SameSite=Lax 送不出去，後端 API 會全部 401、表格空白。解法：靠 cookie session 的看板請與本系統部署在同一 host；走 Windows 整合驗證的不受影響。

另外，開發人員請注意：#main-iframe 的 sandbox 屬性永遠要含 allow-same-origin， 拿掉它會讓被嵌入頁面被丟進 opaque origin（Windows 驗證帶不出身分、cookie 送不出去、storage 直接丟錯）。 Console 那句 allow-scripts + allow-same-origin ... can escape its sandboxing 警告是預期且無害的。

7. 權限控制（核心章節）

7.1 權限模型：一張圖看懂

「某個人能看到哪些看板」是由三層疊出來的，不是單一設定：

第 1 層　群組給的範圍 帳號 ──▶ 可視群組版面(Role) ──▶ 該 Role 允許的看板清單 （Map_Account_Role → Map_Role_Menu） 第 2 層　帳號個別覆寫（綁定廠區） ＋ 額外開放看板 (Map_Account_ExtraMenu) － 個別封鎖看板 (Map_Account_DenyMenu) 第 3 層　看板自己的門禁（ACL，Admin 專用） ＋ 白名單放行 (Map_Menu_AllowAccount) ← 強制加回，蓋過第 2 層的封鎖 － 黑名單封鎖 (Map_Menu_DenyAccount) ← 最終否決，誰都救不回來 最後　沿著父子結構向下展開：父節點看得到 → 子節點自動繼承（遇到 ACL 封鎖就停住不展開）

兩個一定要知道的特例

  • admin 一律全部可見，完全不套用上面的計算。
  • Auth:OpenAccessMode = true 時所有人都全部可見。想讓權限真的生效，這個旗標必須是 false。

「可存取的廠區」怎麼算

＝ 這個帳號的 Role 集合 ∩ 各廠區綁定的 Role。有交集的廠區才會出現在廠區下拉裡。

ℹ 額外開放／個別封鎖是「綁廠區」的 這兩項在設定時必須先選廠區，代表「這個人在這個廠區額外開放／封鎖哪些看板」。
後端在決定「資料要不要送給前端」時採寬鬆策略：只要在任一個可存取廠區被開放，資料就會送； 只有當該看板在所有可存取廠區都被封鎖，才會整個消失。實際顯示則由前端依當前廠區再收斂一次。

⛔ 設定「登入預設首頁」時的陷阱

更麻煩的是連鎖污染：死頁一樣會記錄一次點擊，實測曾讓某張看板的「點擊率」累積到 397 次的假數據。 看到某個看板點擊數異常高，先確認它是不是誰的預設首頁。

挑選器已經會過濾掉打不開的節點，但請確認你選的落點真的能開（是資料夾、或有網址、或是應用集合）。

7.5 單張看板的白名單／黑名單 Admin

在看板網頁管理或選單配置管理的編輯視窗裡，展開 「存取控制（白名單／黑名單）」（僅 admin 看得到這一段）。

欄位行為
白名單一旦填了任何工號，只有名單上的人看得到這張看板，其他人一律擋掉（即使 Role 有給）。白名單放行會蓋過帳號層級的個別封鎖。
黑名單名單上的人一律看不到，優先級最高，Role 與額外開放都救不回來。
  • 格式：每行填一個工號，留空＝不卡控。
  • 對資料夾設定時，整個子樹一起卡控（被擋的人連底下的子看板都看不到，也不會向下展開）。

7.6 排錯 SOP：「某人看不到某張看板」

依序檢查，八成在前三步就找到：

  1. 這張看板是不是被「停用」了？（選單配置管理的開關）→ 停用對所有人隱藏。
  2. 他現在站在哪個廠區？ 權限是分廠區的。請他先切到正確廠區再看。
  3. 他的 Role 有沒有包含這張看板？（權限管理 → 該 Role 的允許清單）
  4. 那個 Role 有沒有綁到他所在的廠區？（廠區管理 → 套用的權限群組）
  5. 帳號層級有沒有把它個別封鎖？（帳號管理 → 進階個別權限調整 → 個別封鎖，記得先選對廠區）
  6. 看板本身有沒有白名單？ 有白名單但他不在名單上＝視同封鎖。
  7. 看板本身有沒有黑名單？ 在黑名單上＝最終否決。
  8. 都沒問題 → 打開帳號設定的「實際可見的看板預覽」對答案；再不行請他登出重整（權限異動後快取會換 ETag，通常會自動更新）。

8. 怎麼指派委派管理者 Admin

8.1 委派管理者是什麼

「委派管理者」＝ 管理層級仍是 User，但被授權可以管理某幾個資料夾底下的看板內容。 典型情境：把「12A 的看板目錄」交給 12A 的窗口自己維護，不必給他 admin。

Admin 可以管全部，包含帳號層級、Role、廠區、ACL │ └─ 委派管理者 只能管「被指定的資料夾 + 其子樹」的看板內容 │ 另外可進入帳號管理（但受主從關係限制，見 §8.3） └─ 一般 User 只能看，不能管理

8.2 指派步驟

  1. ⚙ 系統設定 → 帳號管理，找到目標帳號並按編輯。
  2. 確認管理層級 = User（委派是 User 專屬功能；選 Admin 的話這一段會隱藏）。
  3. 打開「啟用委派管理」開關 → 下方展開細項。
  4. 決定要不要勾「允許變更他人內容」：
    • 不勾：他只能編輯自己建立的看板。適合「讓他自己加東西，但不要動別人的」。
    • 勾選：他可以編輯管轄範圍內任何人建立的看板。這也是「委派整個資料夾子樹」生效的必要條件。
  5. 在「管理目錄」清單勾選他能管理的資料夾。勾一個資料夾＝連同底下整個子樹一起委派。
  6. 儲存。他下次進入系統，側欄就會出現「看板網頁管理」與「選單配置管理」。

8.3 委派者的權限邊界（重要）

一個看板可以被他寫入的四個條件（滿足其一即可）

  1. 他是 admin（不適用於委派者）
  2. 這張看板是他自己建的（不需要「允許變更他人內容」）
  3. 這張看板本身就在他的管理目錄清單裡（直接委派）
  4. 這張看板的任一祖先在管理目錄清單裡，且他有「允許變更他人內容」

主從關係：委派者不能授出他自己沒有的東西

當委派管理者去編輯別人的帳號時，系統會強制套用兩個方向的限制：

  • ① 不可授出自己沒有的：只被委派 A 廠區的人，把別人升成委派管理者時，最多也只能授到 A 廠區。
    • Role 的上界＝他自己擁有的 Role
    • 看板的上界＝他自己能管理的範圍
  • ② 不可拔掉自己範圍外的既有授權：帳號存檔是「先刪後寫」全量覆寫。 如果只擋①，委派者送出一份「看不到 role_3」的表單就會把 admin 給的 role_3 靜默刪掉（降權攻擊）。 所以範圍外的既有設定會被原封保留。

委派者絕對不能做的事（Admin only）

  • 更改任何人的管理層級與允許變更他人內容 —— 提交值會被忽略並寫回 DB 現值（不會報錯，表單本來就不該送這兩欄）。
  • 新增／刪除帳號。
  • 編輯任何 admin 帳號。
  • 匯出帳號清單。
  • 設定看板的白名單／黑名單（整段 ACL 區塊對非 admin 隱藏）。
  • 廠區管理、權限管理、操作紀錄、流量統計、申請審核。
ℹ 挑選器上「灰掉但看得到」的選項是刻意的 在帳號設定裡，超出委派者範圍、但目標帳號已經擁有的項目會以鎖定（disabled）呈現，而不是隱藏起來。 這樣委派者才知道「這個人還有這些權限，只是我不能動」，不會誤以為那些權限不存在。
另外請注意：前端挑選器不是安全邊界，真正的把關在後端 —— 就算繞過畫面直接打 API 也一樣擋得住。

8.4 只被委派「子資料夾」的人怎麼進去管？

如果某人只被委派了深層的某個子資料夾，他在「選單配置管理」的列表上只會看到最上層那一列祖先， 而那一列他是沒有編輯權的。這時該列會出現一個明確標示為「管理子項目」的入口 —— 從那裡進去就能編輯自己被委派的子樹。

（這個入口刻意不叫「編輯」，避免誤導成可以修改該列本身。）

8.5 常見誤解

誤解實際情況
「委派管理者＝小一號的 admin」❌ 他只能管內容，碰不到 Role、廠區、ACL、稽核。
「勾了管理目錄他就什麼都能改」❌ 若沒勾「允許變更他人內容」，他只能改自己建的。
「委派者看得到帳號管理，就能改所有人」❌ 受主從關係限制，且完全碰不到 admin 帳號與管理層級欄位。
「畫面上沒有按鈕就代表安全」❌ 畫面只是體驗；後端有獨立的授權判定，兩邊都有做。

12. 部署與維運 部署／IT

12.1 部署到 IIS

  1. 確認 appsettings.Production.json 或 web.config 內的連線字串是正式 DB。
  2. dotnet publish -c Release -o publish
  3. 把 publish/ 整包放到 IIS 目錄（例如 C:\inetpub\wwwroot\EQDashboard_TEST）。
  4. IIS Manager → 對該目錄右鍵 → 轉換為應用程式。
  5. App Pool 的 .NET CLR 版本設為 「無受控碼 (No Managed Code)」。
  6. IIS Manager → 選此 App → Authentication 面板：
    • ✓ Anonymous Authentication = Enabled
    • ✓ Windows Authentication = Enabled
    • ✗ Basic Authentication = Disabled
    • Windows Authentication 的 Providers 順序：Negotiate → NTLM
  7. 依 web.config 的「設定區 B」決定登入模式（預設 B1＝純 Windows 自動偵測）。
  8. iisreset。
⚠ 為什麼 web.config 裡沒有 <security><authentication> 區段 這是刻意的。多數企業 IIS 把該區段鎖在 server level（overrideModeDefault="Deny"）， 在 app 層級寫會直接觸發 HTTP 500.19。請一律改用 IIS Manager 面板設定。
若真的被鎖死無法在面板改，請 IIS 管理員執行解鎖： appcmd unlock config -section:system.webServer/security/authentication/windowsAuthentication

12.2 HTTP 站台一定要設 Hosting__RequireHttps=false

web.config 內：

<environmentVariable name="Hosting__RequireHttps" value="false" />

漏設的症狀非常有迷惑性：Cookie 會帶 Secure flag，瀏覽器在 HTTP 下不會送回 → 每個請求都被視為未登入 → 看起來就是「登入後立刻被踢回登入頁」。IIS 上了 HTTPS 之後再改成 true。

12.3 切換資料庫（正式區／測試區）

✔ 直接改 appsettings.json 就會生效（2026-08-31 起）

在 IIS 上，把 ConnectionStrings:EQDashboard 改成新的 Initial Catalog（或整條換掉）→ 存檔 → 下一個請求就會連到新的 DB。 不需要 iisreset，也不需要手動回收 App Pool。

怎麼做

  1. 編輯 IIS 站台目錄下的 appsettings.json（不是原始碼資料夾那一份）。
  2. 改 ConnectionStrings.EQDashboard，存檔。
  3. 打開 logs\log-*.txt，會看到這兩行： 
    🔄 偵測到 ConnectionStrings:EQDashboard 變更（新目標 Catalog=EQDashboardV2_TEST，來源 appsettings.json），即將停止本進程…
🗄️ 使用中的資料庫：Server=… / Catalog=EQDashboardV2_TEST / … ｜設定來源：appsettings.json
  4. 重新整理網頁即可。

它背後做了什麼（以及為什麼是這樣做）

系統用的是 EF Core 連線池，連線字串在啟動建立 options 時就被凍住、之後不再重讀 —— 連線池的前提就是 options 固定不變，所以「維持連線池」與「現讀現用」本質上互斥。 因此偵測到連線字串變動時，程式的作法是讓進程停下來，由 IIS 在下一個請求拉起新進程。

選擇換進程而不是「就地換連線」是刻意的：換進程才會一併重跑 SchemaBootstrap（新 DB 可能缺表）、清掉快取與 ETag（否則會拿舊 DB 的資料回應最多 60 秒）、並重印 DB banner。

內建的三道保護

情況行為
只改了空白、或把 Initial Catalog 挪個位置不會重啟（比對前會正規化，純排版編輯不算變更）
連線字串被清空或改壞不會重啟，只記一則錯誤；站台維持用舊連線服務（重啟只會撞上啟動守衛變成空白 500.30，更難救）
改的是 Auth 等其他設定不會重啟（否則存個檔就把所有人踢下線）

預設值與關閉方式

  • IIS / ANCM（會自動拉起新進程）→ 預設 開啟。
  • dotnet run / 自架 Kestrel → 預設 關閉（否則存個檔站台就直接結束、不會再起來）。
  • 要強制關掉（例如正式站不希望「改個檔案」就能無聲換掉全站資料來源），在 web.config 明確指定，這會優先於自動判斷： 
    <environmentVariable name="Hosting__RestartOnConnectionStringChange" value="false" />

仍然存在的一個坑：publish 會蓋掉

⚠ 要長期固定用某個 DB，還是寫在 web.config「設定區 A」

appsettings*.json 是 content 檔，下次 dotnet publish 覆蓋部署就會把手改的值洗掉，而且不會有任何提示。 臨時切換用改檔案很方便；但如果這個站台長期就是要接測試庫，請改成環境變數，它不受 publish 影響：

<environmentVariable name="ConnectionStrings__EQDashboard"
     value="Data Source=...;Initial Catalog=EQDashboardV2_TEST;Integrated Security=True;TrustServerCertificate=True;" />

（或設在 IIS Manager → App Pool → 進階設定 → 環境變數。web.config 一存檔 ANCM 也會自動回收。）

改了卻沒換過去？先看「設定來源」

每次啟動都會印一行（只印 Server / Catalog / 驗證方式 / 來源，絕不印密碼）：

🗄️ 使用中的資料庫：Server=… / Catalog=… / …（環境 =…）｜設定來源：appsettings.json

最後那個「設定來源」就是答案。「我改了 appsettings.json 卻沒換 DB」幾乎都是這兩個原因，而且從值本身完全看不出來：

你看到的來源代表什麼
appsettings.json正常。改這個檔就對了
appsettings.Production.json你改的 appsettings.json 被它蓋掉了 —— 要改的是這一份
環境變數 ConnectionStrings__EQDashboard…被 web.config 設定區 A 或 App Pool 環境變數蓋掉 —— 改那裡

如果來源顯示 appsettings.json、Catalog 卻還是舊的，那就是改到了原始碼資料夾而不是 IIS 站台目錄下的那一份。

連線字串格式寫錯（少引號／分號）也會在同一處以錯誤現形。這行 banner 排在連線 DB 之前印，所以就算切到一個完全連不通的 DB，你仍然看得到它試圖連哪裡。

12.4 搬機器 / 備份時的三個必留項目

項目漏掉的症狀
App_Data/keysDataProtection 金鑰。刪掉＝所有人一起被登出（Cookie 是用它加密的）
wwwroot/lib第三方資源。漏掉＝畫面完全裸奔：純 HTML 樣式、圖示變空框、表格不 render、Modal 按了沒反應

✔ 搬機器請用 git clone / git checkout，不要手動複製檔案 wwwroot/lib 是版控的一部分（.gitignore 刻意沒有 ASP.NET 樣板那條 wwwroot/lib/）， 所以 git clone + dotnet publish 就是完整的。
看到裸奔畫面先查 wwwroot/lib 在不在，不要先懷疑 CSS 被改壞。

12.5 執行期不可有外網相依

Bootstrap 5.3.2 / FontAwesome 6.4.0 / jQuery 3.7.0 / DataTables 1.13.6 / SheetJS 0.18.5 全部自 host。 Program.cs 的 CSP（script-src 'self' / style-src 'self'）是安全網 —— 有人改回 CDN 會被自己的 CSP 擋掉。請改回自 host，而不是放寬政策。

兩項「仍會連外」但不是專案資產的例外：frame-src（看板 iframe 的網址，是 DB 資料）與 img-src（圖示可填外部圖檔 URL）。要治的是 DB 內容 —— 圖示請改用上傳到 wwwroot/images/icons/ 的本地檔。
