Findings
[P0] LDAP 關閉時等同任意密碼放行
AuthService.cs (line 56) 在 Auth:Ldap:Enabled=false 時直接 return true，而 appsettings.json (line 17) 又啟用測試帳號。結果是：只要帳號存在，非測試帳號可能用任意密碼登入。建議改成 LDAP 關閉時 fail closed，只允許明確測試帳號或緊急 admin，且正式環境關閉 TestAccounts.Enabled。

[P0] /Settings/GetInitialData 匿名開放，會洩漏完整資料模型
SettingsController.cs (line 22) 標 [AllowAnonymous]，而 SettingsService.cs (line 18) 會一次讀出 Accounts、Roles、Requests、PersonalSettings、ACL 對照表等 13 張表。這會讓未登入者取得帳號、權限、申請單與選單結構。建議拆分登入前必要資料與登入後資料，並依目前使用者/角色/廠區回傳可見範圍。

[P0] 一般 user 可呼叫帳號管理 API
AccountsController.cs (line 13) 是 [Authorize(Roles = "admin,user")]，導致 user 也能查全部帳號、新增、更新、刪除，且 UpdateAccount (line 101) 可更新 RoleLevel。這是明顯權限提升漏洞。帳號管理 API 應改 admin-only，自我資料另開 MyProfile 類 API。

[P1] 委派選單管理目前只有前端邏輯，後端未落實範圍控管
MenusController.cs (line 59) 的新增/更新/刪除/批次儲存都是 admin-only。這會讓已委派的非 admin 使用者無法真正儲存；若之後簡單開成 user 可用，又會缺少「只能管理授權主選單」的後端保護。建議新增後端授權服務，檢查 Map_Account_ManageMenu、廠區可視權限、CanEditOthers、資料建立者。

[P1] Legacy 全量覆寫 API 可能提交部分成功資料
SettingsService.cs (line 161) 逐表 DELETE/INSERT，但表格處理失敗後只是累積 errorLogs，最後仍可能 Commit (line 302)。匯入或同步時可能造成部分表更新、部分表舊資料遺失。建議任何表失敗就 rollback，或把此 API 限定成匯入用並先完整驗證。

[P1] 側邊選單存在 Stored XSS / inline onclick 注入風險
sidebar-item.js (line 27) 將 menu.url 放入 inline onclick，displayName 也有多處直接進 innerHTML。若委派使用者可新增看板，惡意標題或網址可能注入 JS。建議全面改用 escapeHTML、addEventListener、data-*，並驗證 URL scheme。

[P2] Cookie/CSRF 防護還不完整
Program.cs (line 37) Cookie 是 SameSite=Lax、SecurePolicy=SameAsRequest，且 mutating APIs 沒看到 antiforgery/custom CSRF header。正式環境建議 HTTPS-only、SecurePolicy=Always，並加 CSRF token 或固定自訂 header 驗證。

[P2] V2 架構有 Service 層，但帳號管理仍繞過 Service
IAccountService 已註冊，但 AccountsController.cs (line 15) 直接操作 AppDbContext。這會讓授權、委派、資料一致性規則分散。建議帳號 CRUD 收斂到 Service，Controller 保持薄層。

   sidebar-item.js (line 27) 不要把 DB 來的 url/displayName 直接塞進 innerHTML 或 inline onclick。
